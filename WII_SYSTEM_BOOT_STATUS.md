# User-provided Wii system data and boot path

BroadwayCPU now has an **inventory-only** reader for an extracted NAND tree. It parses the System Menu TMD, follows its System Version field to the required IOS title, and checks for the TMD, tickets, the System Menu boot-index content, and **every content file declared by the IOS TMD**. Normal content is resolved by content ID; shared content is resolved by the TMD SHA-1 through `/shared1/content.map`. It does not authenticate metadata, decrypt title contents, verify content hashes against decrypted bytes, load code, or execute the Wii boot chain. The GUI exposes this through **Tools → Configure Wii system data...**; ISO selection remains independent. The TMD field offsets and content table layout follow the documented format: System Version at `0x184`, Title ID at `0x18c`, content count at `0x1de`, boot index at `0x1e0`, and content records from `0x1e4`.

## Files currently in the repository

The repository contains `rootca.pem`, `clientca.pem`, and `clientcakey.pem`. Inspection shows that the first two are DER-encoded X.509 certificates whose issuer/subject identify Nintendo CA certificates; `clientcakey.pem` is DER-encoded RSA private-key material. The `.pem` suffix is therefore a container-name mismatch, not evidence that these are executable boot ROMs. These certificate files are not loaded as firmware, keys, Starlet code, or Broadway state.

The later supplied directories change the NAND finding: the repository now contains an extracted NAND tree. The firmware probe reports System Menu metadata and boot content present, required IOS title `0x0000000100000050` (IOS slot 80), all 15 IOS content records resolvable, and both tickets present. Several `/shared1/*.app` files begin with an ARM ELF header; the tree therefore contains Starlet-side executable content. The System Menu boot content begins with a Wii executable/container header rather than an ELF header. This is genuine firmware data, but the project still has no ARM interpreter, IOS kernel/module loader, NAND crypto/authentication path, or boot2 execution path, so these files are not executed yet.

## Processor responsibilities

- **boot0, boot1, boot2:** execute on Hollywood's ARM Starlet. boot0/boot1 establish and authenticate the next boot stage; boot2 is a small IOS-derived loader that locates and launches the IOS required by the System Menu.
- **IOS:** executes on Starlet. It supplies the Wii-specific device and title services, including NAND, ES/title launch, optical-disc access and the Broadway IPC path. IOS is not Broadway code and its responses cannot be replaced by arbitrary syscall return values.
- **System Menu and BS2:** execute on Broadway. The menu handles the user-facing state; its BS2 disc-launch state machine starts the apploader, services its reads through the disc interface, loads the DOL/FST, and transfers control to the game.
- **Revolution OS:** game-side Broadway runtime. It installs exception dispatch and OS state. Public Revolution OS documentation identifies `OSInit`/`__OSInitSystemCall` as the normal owner of the system-call vector at `0x80000C00`; the game apploader is entered before the game DOL's ordinary OS initialization. The exact handler bytes and startup memory contract for RGHP52 have not yet been established from Nintendo firmware or a verified independent specification.

Thus the smallest credible route to GH3's apploader is not a cold reset plus a fabricated vector. It is a boot environment that loads the relevant IOS and System Menu/BS2 behavior, or a separately validated, exact implementation of their handoff and services. The latter is not currently available in BroadwayCPU. The GS/strap warning is normally game/system startup content, but reaching it still requires title launch and IOS-backed device interaction; no evidence presently establishes that main.dol alone can display it.

For the firmware route, the minimum useful user data is a mutually consistent NAND image/tree containing the System Menu title, the IOS title named by its TMD (including its full module content set), tickets, and the boot2 material/state needed to enter that IOS. boot2 is a special boot title stored outside the normal `/title/00000001/...` extracted-title layout, so this inventory explicitly reports it as unknown. A directory extracted only from `/title` cannot establish the complete cold-boot chain. Even with those files, BroadwayCPU still needs Starlet execution, NAND/title decryption with user-supplied console secrets, IOS/ES/IPC behavior, and the Broadway/System Menu handoff. To reach a game, BS2 must also issue the disc/apploader reads and establish the launch state expected by the apploader. To reach video, the game must then execute its own startup and produce GX commands and XFB copies.

## Current evidence and limits

### EXI register and DOL polling

The Wii PPC-side address `0xCD00680C` is EXI channel 0's control register (`EXI_CR`), not an SI register. Nintendont's [`EXI_ADDR(channel)` definition](https://github.com/FIX94/Nintendont/blob/master/resetstub/exi.h) uses `0xCD006800 + channel * 0x14` and identifies offset `0x0C` as `EXI_CR`. The DOL independently computes that same address from its channel argument. The [WiiBrew EXI register reference](https://wiibrew.org/wiki/Hardware/EXI) documents the register fields and channel/device assignments; its table lists a different base (`0x0D806800`), so the PPC-side address here is grounded in the matching DOL access and Nintendont definition rather than silently treating that table address as identical. The model also accepts the `0x0D006800` uncached alias of the PPC `0xCD006800` address. The older `0xCC...` C-bank mapping remains separate and does not alias this Wii D-bank controller.

The register block has three channels with a `0x14`-byte stride and CSR, DMA address, DMA length, control, and immediate-data registers. The model supports big-endian byte, halfword, and word accesses, register byte lanes, CSR write-one-to-clear interrupt status bits, and separate C/D-bank state. Reads do not mutate register state. `EXI_CR` fields are `TLEN[5:4]`, `RW[3:2]`, `DMA[1]`, and `TSTART[0]`; `TSTART` starts a transfer and the documented controller behavior is to clear it when the transfer completes. A zero `TSTART` is idle; a set `TSTART` is a pending/busy request. `EXI_CSR` exposes chip select, clock, interrupt status/masks, and channel-0 ROMDIS; the EXT presence bit is read-only and interrupt status bits are write-one-to-clear. The hardware references reviewed do not specify the outcome of a transaction with no device selected, nor do they give silicon reset values for this register block. Consequently, the model's zero-initialized state is an emulator initialization choice, not a claimed hardware reset value. BroadwayCPU has no EXI transfer engine or EXI device implementation yet; it preserves `TSTART` rather than inventing a completion or interrupt. This is consistent with the no-device path in [Dolphin's EXI channel implementation](https://github.com/dolphin-emu/dolphin/blob/master/Source/Core/Core/HW/EXI/EXI_Channel.cpp), which returns without clearing `TSTART` when the selected device is absent, but that emulator behavior is not proof of undocumented silicon behavior.

The DOL trace shows the call at `0x800285A4` starting a channel-0 immediate write; the caller supplies a two-byte transfer, and the resulting `EXI_CR` is `0x15` (`TLEN=1`, write, immediate mode, `TSTART=1`). Its wait routine at `0x80027DB4` computes `0xCD00680C` from the channel number (`mulli` by `0x14`, add base `0xCD000000`, then add `0x680C`), loads the register at `0x80027DC0`, masks bit 0 at `0x80027DC4`, and branches back at `0x80027DC8` while that bit remains set. The loop can exit only when `TSTART` becomes zero. The first instruction after the loop is `0x80027DCC: or r10,r9,r9`; the routine then restores MSR state and returns to `0x800285B0`, where the caller proceeds to its next transfer.

WiiBrew identifies channel 0 CS2 as the former GameCube serial port, unused on Wii. The observed `EXI_CSR=0x2200` selects CS2 and sets ROMDIS; `EXI_CR=0x15` requests a two-byte write. The model has neither a device attached to CS2 nor an EXI transfer engine, so it leaves the request pending; the references do not establish whether real silicon clears `TSTART` for this no-device transaction. Clearing it merely to leave the loop would be unjustified. The initial EXI CSR/CR values are both zero in the model. The earlier diagnostic display `r9=15` was formatted in hexadecimal and therefore means `0x15`, not `0xF`; after the `andi.` instruction the polling value is `0x1`.

The C and D MMIO banks are kept separate, the prior conflicting all-ones/zero overrides are removed, and the DOL diagnostic no longer writes status values or uses a breakpoint to escape polling loops.

The direct apploader diagnostic decrypts RGHP52's game partition, loads the apploader image and executes 360 instructions. Its `sc` enters the architectural exception vector; the next fetch at `0x00000C00` sees zero. No apploader callbacks complete, no game DOL is loaded, and no GX commands or frames are produced. This is a useful CPU diagnostic, not a real disc launch.

The separate `Wii_Hello_World.dol` diagnostic begins at `0x80004000` with EXI CSR/CR at zero and executes 200,000,000 instructions. It ends at `PC=0x80027DC4` in the EXI wait loop with `r2=0x8003FC14`, `r3=0`, `r4=0x8004FB74`, `r6=0x8004FB75`, `r9=0x15`, `r10=0xCD00680C`, `r11=0`, `LR=0x800285B0`, `MSR=0x2032`, and `CTR=0`. The observed EXI totals are 66,464,133 reads, 10 writes, one TSTART request, and zero modeled completions; final channel-0 state is CSR `0x2200`, CR `0x15`, MAR/length/data `0`. The polling condition did not change, so the loop did not complete naturally or reach its following code. GX command and frame counts are both zero; no genuine frame appeared.

The CMake Debug and Release core builds and CTest each pass (152 checks in the direct test executable). The Win32 GUI target was not built in this MSYS2/GNU validation environment. The homebrew DOL result is not evidence of System Menu or commercial-game boot.

Firmware inventory only establishes that expected extracted files are present. It does **not** establish that they are original, mutually consistent, complete, cryptographically valid, decrypted, or runnable. The firmware directory must be supplied by the user; this project neither downloads nor includes proprietary firmware or keys. A real boot additionally needs an ARM/Starlet execution model, NAND/title decryption and authentication as applicable, IOS modules and IPC, ES launch behavior, DI callbacks, Broadway handoff state, and then the already separate CPU/GX execution path. Missing contents are reported as missing rather than emulated with invented data.

The inventory's synthetic test fixture validates parser/path logic only. Its zero-byte-like `.app` and ticket fixtures are not firmware and must never be interpreted as bootable components.
