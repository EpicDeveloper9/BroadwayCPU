# GX command and video milestone

This is a narrow hardware path, not a complete GX implementation. BroadwayCPU has now rendered and presented a frame from compiled Wii homebrew GX commands.

## Implemented path

- `GXProcessor` receives Broadway CPU writes to the cached (`0xCC...`) and physical (`0x0C...`) CP, PE, and write-gather FIFO windows. Its FIFO parser handles NOP/cache-invalidate, CP, XF, and BP register-load packets, plus PE alpha-configuration and alpha-mode register state.
- The supported primitive subset is `GX_QUADS` with direct XYZ/F32 positions and RGBA8 color0 attributes. Position-matrix, projection, viewport and scissor state feed vertex transformation; vertex colors are interpolated during EFB rasterization.
- The 640×528 EFB is copied to emulated MEM1 as limited-range BT.601 YUYV and the owned frame is published through the existing mailbox. The separate Video Output window consumes that frame. The tested guest frame contains a full-screen four-color interpolated quad.
- Gekko WPAR SPR 921 is modeled as a privileged, 32-byte-aligned target register with an empty write-gather indication; L2CR SPR 1017 has software-visible configuration state. CPU stores to the mapped FIFO port are forwarded in order. WPAR-selected noncacheable-store matching, 128-byte gather-buffer/burst timing, and L2 cache contents/timing are not modeled.
- The GUI accepts `--load <DOL-or-ELF> --run --video` for repeatable test launches. Add `--capture <BMP-path>` to save the current frame held by the Video Output window after it receives a guest frame. The diagnostic video mode remains separately controlled by the View menu and is not enabled by these options.

## Genuine homebrew validation

`tools/wii_gx_smoke/main.c` is a libogc GX producer compiled as a Wii DOL. The test-specific `tools/wii_gx_smoke/build/wii_gx_smoke_gx_probe.dol` is generated by `patch_dol.py`, which bypasses unsupported DSP bootstrap and IPC initialization; it is not an unmodified cold boot. The guest sets a 640×528 viewport, configures direct XYZ/F32 and RGBA8 attributes, draws a four-vertex quad colored red, green, blue, and yellow, then repeatedly calls `GX_CopyDisp`. It does not submit an EXI transfer. This is actual guest instruction/FIFO activity, not a host-generated test image.

At the 1,000,000-instruction probe limit:

- Final PC was `0x80009784` after 999,999 executed instructions; the first primitive was submitted at PC `0x800059F8`, and the first frame copy occurred at PC `0x80009728`.
- EXI recorded three reads, three writes, no transfer starts, and no completions.
- GX recorded 30,652 processed commands, 692 primitives, 233,840,640 EFB pixel writes, and 691 frame copies. It did not stall.
- The published frame was 640×528 YUYV; measured luma ranged from 41 to 210, with center luma 61.
- In the final Windows GUI run, the main window showed Broadway at PC `0x80009940`; its status reported 3,823 GX commands, 82 primitives, 82 frame copies, 11 successful Direct2D Video Output presentations, and an accepted frame. The in-process capture of that current guest frame visibly shows the expected interpolated four-corner color gradient.

The supplied `RandoffAdventures.elf` remains unsuitable for this graphics test: it stalls during startup polling `0xCD00680C` (`EXI_CR`) with one transfer start, zero completions, and no GX commands. The GX smoke DOL avoids that startup path; it does not fix or conceal the EXI limitation.

The app's `--capture` output is a BMP of the exact `VideoFrame` currently owned by the Video Output window, not a screenshot of the whole Windows desktop. The validation frame was converted to PNG for inspection at `tools/wii_gx_smoke/build/genuine_homebrew_video_output.png`; the running app window/status capture is `tools/wii_gx_smoke/build/gx_probe_main_window.png`.

## Explicitly unsupported

Only direct XYZ/F32 + RGBA8 `GX_QUADS` are rendered. Indexed attributes, other primitive types, display-list calls, texture decode/sample, general TEV, lighting, clipping, depth testing, alpha/blend behavior, antialiasing, complete copy filtering/gamma, and general CP/PE behavior remain unsupported. Unsupported FIFO opcodes stall with a diagnostic; unsupported MMIO reads/writes fail instead of returning invented data. The implementation is not sufficient to boot a retail game or render the Guitar Hero III wrist-strap warning. The guest probe also bypasses DSP/IPC startup and supplies fixed video dimensions rather than initializing the full Wii VI/IOS environment.

## RGHP52 startup investigation

The extracted disc metadata identifies `RGHP52` (Europe, revision 1). `DATA/sys/main.dol` is 4,339,360 bytes; it contains two nonempty text sections and eight nonempty data/BSS sections. The extracted system directory also includes `apploader.img`, `boot.bin`, `bi2.bin`, and `fst.bin`. The current loader maps the DOL only and does not execute the apploader or initialize the Wii boot environment, IOS/Starlet, DVD, VI, controller, or interrupt services.

The RGHP52 probe loaded the DOL entry at `0x8000403C` and executed 100,000 instructions. It remained in early startup initialization code ending at `0x800043FC` and produced zero GX frame copies. This is a DOL-only CPU attempt, not a successful Wii game boot.

Nintendo's Wii Optical Disc Drive Guidelines section 5.1 says a game should use only the DOL to display the wrist-strap usage screen before reading other files, and allows an exception when the DOL alone cannot display it. This distinguishes the game startup warning from the Wii System Menu health screen. The screen is expected from the game startup path; reaching it still depends on correct boot context and the game routines that submit GX commands.
