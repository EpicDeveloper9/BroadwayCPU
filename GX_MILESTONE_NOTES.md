# GX command and video milestone

This is a narrow hardware path, not a complete GX implementation.

## Implemented path

- `Memory` can delegate mapped accesses to a separate `MemoryMappedDevice`.
- `GXProcessor` receives writes to the Broadway cached (`0xCC...`) and physical (`0x0C...`) CP, PE, and write-gather FIFO windows.
- The FIFO parser accepts one-byte NOP/cache-invalidate commands and the documented CP, XF, and BP register-load packet forms. It records CP/XF/BP register state and processes the currently modeled display-copy BP registers.
- A 640 by 528 host EFB surface supports direct test pixel setup. The supported EFB-to-XFB copy writes limited-range BT.601 YUYV data into emulated MEM1 and publishes an owned `VideoFrame` to the existing mailbox. The video window remains a separate presentation consumer.
- Gekko WPAR SPR 921 is modeled as a privileged, 32-byte-aligned target register with an empty write-gather indication; L2CR SPR 1017 has software-visible configuration state. CPU stores to the mapped FIFO port are forwarded in order. The WPAR-selected noncacheable store matching, 128-byte gather buffer/burst timing, and L2 cache contents/timing are not modeled.

## Explicitly unsupported

Primitive commands, indexed XF loads, display-list calls, texture decode/sample, vertex processing, clipping, rasterization, TEV, depth/alpha/blend behavior, antialiasing, copy filtering/gamma, and general CP/PE register behavior are not implemented. Such FIFO opcodes stall with a diagnostic; unsupported MMIO reads/writes fail instead of returning invented data. The EFB host surface is not a claim that EFB hardware formats or raster operations are modeled.

Consequently, this milestone can verify command ingress and EFB-to-XFB delivery with deterministic test pixels, but it cannot yet render a game scene or the Guitar Hero III wrist-strap warning. No safety image is embedded or generated by the output window.

## RGHP52 startup investigation

The extracted disc metadata identifies `RGHP52` (Europe, revision 1). `DATA/sys/main.dol` is 4,339,360 bytes; it contains two nonempty text sections and eight nonempty data/BSS sections. The extracted system directory also includes `apploader.img`, `boot.bin`, `bi2.bin`, and `fst.bin`. The current loader maps the DOL only and does not execute the apploader or initialize the Wii boot environment, IOS/Starlet, DVD, VI, controller, or interrupt services.

The RGHP52 probe loaded the DOL entry at `0x8000403C` and executed 100,000 instructions. It remained in early startup initialization code ending at `0x800043FC` and produced zero GX frame copies. This is a DOL-only CPU attempt, not a successful Wii game boot.

Nintendo's Wii Optical Disc Drive Guidelines section 5.1 says a game should use only the DOL to display the wrist-strap usage screen before reading other files, and allows an exception when the DOL alone cannot display it. This distinguishes the game startup warning from the Wii System Menu health screen. The screen is expected from the game startup path; reaching it still depends on correct boot context and the game routines that submit GX commands.
